# The myBlu ticket API: changelog

One dated line per change to the contract — `lib/api/schemas.ts`, published as
`docs/myblu-api.openapi.json` and explained in `docs/myblu-api.md` — newest
first. The newest date is the document's `info.version`, and
`lib/api/openapi.test.ts` holds the two together. The API changes by addition,
so a line here says what was added and from which stage it is served; a line
that takes something away is a line about `/api/v2`.

A contract is published when it merges into `dev`. A change made before that,
on the branch that publishes it, amends the line it will merge under rather
than adding one, and the branch's commits to the document are squashed into one
before the merge: a date names one document, and no commit on `dev` carries
another under it. A stage of a stack is its own document: its line is dated
when it is written, and moved to the day it merges when an earlier stage has
published that date first, so no two merges into `dev` share one.

- 2026-11-16 — Stage 5's corrections, made before the release that serves them: `GET /tickets?trackingNumber=` matches whatever the number's case and hyphens, as the platform's numbers are read everywhere else, so a number typed in lower case is found by the platform's own; and `support` is left out of a `GET /config` whose hours the server could not read, rather than failing the answer every new token is checked with.
- 2026-11-16 — Stage 4's corrections, made before the release that serves each operation, so no app build depends on what they replace. A message's `text`, on both sends and in both encodings, and the survey's `comment` (stage 8) refuse U+0000 as `400 invalid_request` naming the field, and publish the same `pattern`. A cursor is still opaque and `invalid_cursor` still means "drop it and load the newest page", but the server now signs each one, so `listMessages`' example shows a signed cursor, and one built by hand is refused. `tickets.maxOpen` (`GET /config`, stage 3) says what it bounds: opening a ticket, which `POST /tickets` refuses `409 too_many_open` past it, and not a reply, which reopens a resolved ticket whatever the count. A poll's `olderCursor` (`listMessages` with `after`) is always null, as its description now says: a poll never pages back, and the cursor it carried named its first row, which was as often one the overlap re-read, so it was not null at the start of the thread. `revokeSessions`' `account_deleted` and `number_released` say what becomes of the tickets that leave the app: they stay with the support team, and an open one is resolved there.
- 2026-11-13 — Two of stage 3's operations, corrected before the release that serves them, so no app build depends on what they replace: `POST /sessions` refuses a `name` or a `client.appVersion` holding U+0000 as `400 invalid_request` naming the field, and both publish the `pattern` that says so, since the database cannot store that character and the mint answered `500`; and its `name` keeps the contact's name current, a new contact taking it and an existing one brought up to date with it on every mint where the two differ, where it was used only for a contact the mint created. `DELETE /session` no longer lists `403 blocked`: a blocked user's session is ended and answered `204`, as any other, rather than left live for the rest of its day. Nor `426 client_upgrade_required` and `400 invalid_request`: it judges no `ShipBlu-Client`, published there as optional, so a build too old to be served, or one whose header no longer parses, still ends its session.
- 2026-11-12 — First publication, stage 0b of `plans/myblu-ticket-api.md`: every operation's shapes, the error body and its nineteen codes, the webhook's `message.created` and `survey.created`, and the push payload. Every wait and lifetime is a whole number of seconds, at least 1. Every limit on text is counted in UTF-16 code units: the two on what the app's user writes are published where a client reads them (`limits.messageMaxChars`, and the survey's own `commentMaxChars`), and the session's `name`, which only the backend sends, says so in its description. On the server plane each refusal says what the backend does with it rather than what an SDK does: `POST /sessions` names the three it relays to its app as they came, and the rest it answers with a `502` of its own. Served now: `GET /openapi.json` alone; each other operation names the stage that serves it (`x-shipblu-stage`).
